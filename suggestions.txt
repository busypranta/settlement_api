Settlement API - Security Issues & Feature Suggestions
======================================================

Date: 2026-10-28
Repository: settlement_api

## SECURITY ISSUES

### Critical
1. **Hardcoded/Default Security Concerns**
   - [DONE] SECRET_KEY must be set via env; ensure it's not committed. .env exists in repo - in .gitignore and read via django-environ. Must remain not committed in prod.
   - [DONE] Secure headers added: SECURE_SSL_REDIRECT (when not DEBUG), SECURE_HSTS_SECONDS (when not DEBUG), SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE, SECURE_CONTENT_TYPE_NOSNIFF, X_FRAME_OPTIONS='DENY'.
   - [TODO] ALLOWED_HOSTS needs proper prod config (defaults to ['localhost', '127.0.0.1']).

2. **Authentication/Authorization**
   - [DONE] JWT tokens have 2h access lifetime. ROTATE_REFRESH_TOKENS=True, BLACKLIST_AFTER_ROTATION=True enabled with token_blacklist app. Logout/blacklist endpoint added (/api/v1/auth/token/logout/). Refresh token rotation tested.
   - [TODO] API playground in portal stores tokens in page memory only (good) but need to ensure no localStorage.
   - [TODO] For admin APIs, some views check role flags in multiple ways (role field + is_superuser) - can be confusing; ensure consistent checks.
   - [DONE] User creation allows setting role only to USER/ADMIN, preventing privilege escalation via is_superuser/is_staff flags. Enforced in UserListCreateView. API docs/schema filtered by role.

3. **Input Validation & Injection**
   - [DONE] Services use ORM properly with .using('source') and filter by params - safe from SQL injection via ORM. Direct SQL only in health check (SELECT 1 FROM DUAL) - safe.
   - [DONE] Date parsing uses DRF DateField with specific format (%d-%m-%Y). Settlement report limited to 60 days.
   - [DONE] Merchant name matching uses casefold/normalized keys (PortalMerchant.merchant_name_key, normalize_name_key) - helps avoid collisions.
   - [DONE] SettlementTransactionsView does pagination with slicing after count(); page size 200. No raw SQL string concatenation.
   - [TODO] Merchant name filtering in transactions uses `merchant_name__iexact` against source DB - ensure case/whitespace consistency (source data may vary). Currently matched via normalization in settlement logic; transactions rely on iexact on merchant_name.

4. **Data Exposure**
   - [DONE] APILogMiddleware catches exceptions, logs them, returns generic "Internal server error" with request_id. For non-JSON API responses it replaces with generic message.
   - [DONE] core/exceptions.py wraps DRF errors as {'success': False, 'errors': ..., 'request_id': ...}. Stack traces not exposed when DEBUG=False (Django default).
   - [TODO] ApiLog stores client_ip (GenericIPAddressField) - ensure PII handling/compliance if required.
   - [TODO] AuditLog stores metadata as JSON - ensure no secrets logged.
   - [DONE] Health endpoint (AllowAny, no auth) returns only status - doesn't leak DB details.

5. **Cross-cutting Concerns**
   - [DONE] CSRF protection enabled (good for session auth). API uses JWT so CSRF less of an issue for API calls, portal forms protected.
   - [TODO] CORS not explicitly configured in visible settings - if frontend served separately, need django-cors-headers. Not shown in requirements.
   - [DONE] X_FRAME_OPTIONS = 'DENY'. SECURE_CONTENT_TYPE_NOSNIFF = True. SESSION_COOKIE_SECURE/CSRF_COOKIE_SECURE depend on DEBUG.
   - [DONE] WhiteNoise for static files. media/ exists but no obvious file upload endpoints in current codebase.
   - [DONE] Rate limiting configured (300/hour user, 30/hour anon). Throttling applied via REST framework defaults.

6. **Business Logic Security**
   - [DONE] Settlement transactions status determination relies on matching APPROVED settlement lines by merchant name normalization - logic correct per README. Portal has unique normalized merchant_name_key and UID.
   - [DONE] Merchant assignment/management has proper scoping (admins can only manage scoped users/merchants). Permissions logic enforced.
   - [DONE] "Multiple-merchant API access" disabled by default for USER role - enforced in SettlementReportMultiView. Also controlled via allow_multiple_merchants flag (added in migration 0004). "Settlement transactions API access" controlled via allow_settlement_transactions (added in migration 0005).
   - [DONE] Source DB is read-only enforced by router (raises PermissionDenied on write) - defense in depth.

### Medium
1. **Logging & Monitoring**
   - [TODO] APILogMiddleware logs exceptions but only exception type/name; consider structured logging with request context. Also ensure logs don't contain sensitive data.
   - [TODO] ApiLog stores http_status, duration, etc - good for audit. But consider log retention/rotation.
   
2. **Session Security**
   - [DONE] Using Django sessions for portal (alongside JWT for API). SESSION_COOKIE_SECURE tied to DEBUG.
   - [TODO] Consider SESSION_COOKIE_HTTPONLY, SESSION_COOKIE_SAMESITE, SESSION_EXPIRE_AT_BROWSER_CLOSE, etc.

3. **Error Messages**
   - [DONE] Some error messages are generic (good), others like IntegrityError give specific messages - mostly fine.

## FEATURE SUGGESTIONS

### Security Enhancements
- [DONE] Enable JWT token rotation with blacklist (token_blacklist in INSTALLED_APPS, ROTATE_REFRESH_TOKENS=True, BLACKLIST_AFTER_ROTATION=True). Logout/token blacklist endpoint added (/api/v1/auth/token/logout/).
- [PARTIAL] Add security headers middleware configuration (HSTS, SSL redirect added; Referrer-Policy, Permissions-Policy missing). Django 4+ has SecurityMiddleware; consider django-csp or custom headers.
- [ ] Implement account lockout after failed login attempts (django-axes or custom). Login is via DRF SimpleJWT token obtain and Django portal auth - need to protect both.
- [ ] Add 2FA/MFA for privileged roles (SUPERADMIN/ADMIN).
- [ ] API key authentication option for service accounts? Or IP allowlisting.
- [ ] Add request signing for sensitive operations.
- [ ] Implement audit log export/archival and better search.
- [ ] Add data masking in logs for PII (mobile, emails).
- [ ] Content Security Policy for portal UI.
